# Android Release Shell Backlog

The shipping Android product is the generic SDL/AOT shell generated by
`stasis package-mobile`. It intentionally contains no Workshop editor, compiler,
JIT, Codex bridge, tests, or writable Stasis source.

The current shell provides app identity/version/orientation from `stasis.json`,
arm64 AOT execution, SDL graphics/audio/input/lifecycle handling, packaged
sprites and fonts, app-private storage, a three-finger performance overlay,
safe-inset-aware fatal diagnostics, and startup SHA-256 verification of every
asset declared by `assets/manifest.json`.

## Potential additions

1. Game-specific adaptive icons and launch artwork. Add manifest fields and
   generated Android resources without putting game identity back into Gradle.
2. Release signing and Play publishing. Keep keystores and credentials outside
   the generated project; accept signing configuration only at the publishing
   boundary.
3. Test-only x86_64 AOT output. Restore Workshop-versus-release renderer parity
   on `Stasis_API_35` without distributing x86_64 in the Play bundle.
4. Crash-loop and redacted support diagnostics. Persist bounded status codes and
   symbol-free native crash metadata; never include game state, user content,
   credentials, or absolute paths without explicit consent.
5. Stronger package attestation. The current runtime verifies declared asset
   hashes. A later layer could verify a signed whole-package manifest or Play
   Integrity result when the threat model requires authenticity as well as
   accidental-corruption detection.
6. Accessibility semantics for game-defined controls and status. A generic
   surface description is possible now, but useful screen-reader interaction
   requires a small game-to-platform semantic tree contract.
7. Controller, haptic, and keyboard mappings. SDL already supplies the device
   events; Stasis needs a stable stdlib-facing mapping and deterministic tests.
8. Platform services behind optional adapters: achievements, leaderboards,
   cloud saves, billing, notifications, deep links, and analytics. Keep each
   adapter opt-in so unused SDKs add no permissions, startup work, or file size.
9. Delivery-size reporting. Record AAB size, estimated arm64 download/install
   size, native-library contribution, assets, symbols, and regression thresholds
   in release CI.
10. Asset-copy optimization. Verify package assets once per version and retain a
    validated version marker so large games do not recopy and rehash unchanged
    content on every launch.

Add these only through the generic shell or an explicit optional adapter. Do not
reintroduce game-specific Android runtime flavors.
